# What This Project Actually Is

Read this first. [REPORT.md](REPORT.md) is the design write-up — the decisions and their trade-offs. This is *what the project is and why anyone wants it*, in plain language.

---

## 1. The business problem, in plain terms

interface.ai sells AI agents to banks and credit unions. A member calls in and says "what's my savings balance?" — the AI agent needs to actually go and find out.

If the bank's system has an API, you call the API. Done. **That case is explicitly out of scope for this project.**

The problem is the other case. Credit unions run a long tail of ancient internal software — core banking screens, servicing tools, admin consoles — written in the 1990s and 2000s, with no API of any kind. The *only* way to get data out or work done is the way a human teller does it: log in, type into a form, click a button, read the screen.

So the question this project answers is: **how do you give an AI agent hands, so it can operate software that was never designed to be operated by anything but a person?**

## 2. The naive answer, and why it fails

The obvious answer is: point an LLM at the screen every time. Let it look, think, and click.

That fails in production for four reasons:

| Problem | Why it's fatal at a bank |
|---|---|
| **Cost** | Every balance lookup burns tokens on re-reading a screen that hasn't changed in six years. Thousands of calls a day. |
| **Latency** | A member is on the phone. An LLM reasoning through five screens takes 30+ seconds. |
| **Non-determinism** | The same request can take a different path on different days. Auditors hate this. Regulators hate this more. |
| **Risk** | A model that "figures it out" each time can, one day, figure out something wrong — on a screen that moves money. |

## 3. The actual answer — the one sentence that defines this project

> **The model discovers. The artifact becomes a reusable capability. Deterministic replay is how the AI agent invokes it in production.**

That's from the brief, and everything you build serves it. Concretely, it's two phases:

**Phase one — discovery. Happens once. Slow, expensive, smart.**
An engineer says: *"Look up member 100042 and read their savings balance."* An LLM opens the app, looks at the screen, and figures it out by trial and error — click here, type there, read that. It's allowed to be slow. It's allowed to cost money. It happens once.

**Phase two — replay. Happens forever. Fast, cheap, dumb, safe.**
While the LLM was exploring, the system was *recording* — not the model's chatter, but what actually worked. It compiles that into a **capability artifact**: a typed, versioned JSON file describing the flow. From then on, the AI agent calls the capability by name with a member ID, and a deterministic engine re-runs those exact steps with **no model in the loop at all**. Same input, same steps, same output, every time. Milliseconds, not seconds. Fractions of a cent. Auditable.

**Record once. Replay many.** That's the whole idea.

## 4. Why this is a hard problem (what they're really testing)

If it were just "record clicks and replay them," it'd be a weekend project. Four things make it hard, and each maps to a rubric row.

### (a) You can't record selectors, because there's nothing stable to record

Modern web apps have `data-testid="search-button"`. Legacy bank apps have this:

```html
<input type="submit" id="ctl00_ContentPlaceHolder1_grdMembers_ctl03_btnSearch" class="f7">
```

That ID is generated by the server and **changes on every page render**. Record it today, it's dead tomorrow. Same for CSS classes (`.f7`), same for XPath (the table nesting shifts).

**What's actually stable is what a human sees**: there's a button, and it says "Search."

So the system records an *identity* — role (`button`) plus accessible name (`"Search"`) plus data context (*the row where the Member ID cell says 100042*) — and re-derives a selector at replay time. That's the **locator ladder**: 7 ranked strategies, try them in order, require exactly one match.

This also happens to be the answer to "how would this work on a desktop app?" — because role-and-name is the one concept that exists in the browser accessibility tree, in Windows UI Automation, in macOS Accessibility, *and* in a human operator's head.

### (b) "Not found" is an answer, not a crash

The brief calls this out as **"the most common design mistake here."**

If you ask for member 999999 and the screen says "No records found" — that is **correct behaviour**. The system worked perfectly. The caller needs to hear "no such member," not "automation failed."

So results are split three ways, and this distinction is load-bearing:

| Class | Example | What the system does |
|---|---|---|
| **Business outcome** | "No such member", "not authorized", "invalid ID" | Return it cleanly as a *declared, typed result*. Not an error. |
| **Recoverable** | Page loading slowly, a "scheduled maintenance" popup, session expired | Handle it — retry, dismiss, re-login — bounded and logged. Then carry on. |
| **Hard failure** | The button genuinely isn't there; the app returned a 500 | Stop. Dump a screenshot, the accessibility snapshot, and a trace. Report *what step, what was expected, what was observed.* |

The clever bit: the business outcomes are **declared in the artifact as data** — a list of detectors — not hidden in `try/except`. So a calling AI agent can read the capability's contract and know in advance that `MEMBER_NOT_FOUND` is a thing that can come back.

### (c) Sometimes it gets stuck, and a human has to take over — the *same* session

Not a fresh browser. The *same* one, with the same login, the same half-filled form, the same scroll position.

That means the system needs a real answer to "who is driving right now?" — a **control lease**. Automation holds it. When it gets stuck, it *cedes* the lease and parks. A human operator opens a console, sees why it stopped and what the screen looks like, takes control, fixes the thing, and hands back. Automation then **re-orients** — it re-reads the screen and works out where it actually is, because the human may have done more, less, or something different than expected.

And while the human holds the lease, automation *cannot act*. Not "politely waits" — structurally cannot. That's the difference between a real control-transfer model and a boolean flag.

### (d) It's regulated financial data

Account numbers, balances, SSNs. So: an allowlist of what the agent may do, risky actions (anything irreversible, like moving money) gated behind explicit human approval, and **redaction everywhere** — logs, screenshots, saved artifacts, and the prompts sent to the model. The model never sees a real member's data; it sees `«param:memberId»` and the system substitutes the real value locally.

## 5. What you're actually shipping

One command chain that runs end to end:

```
                    ┌──────────── DISCOVERY (once, with an LLM) ─────────────┐
   "Look up member  │                                                        │
    100042 and read │   LLM ⇄ observe → decide → act ⇄ hostile legacy app    │
    their savings   │                    │                                   │
    balance"        │                    ▼                                   │
                    │        Recorder → Compiler                             │
                    └────────────────────┬───────────────────────────────────┘
                                         ▼
                          capability artifact (typed JSON, versioned)
                                         │
                    ┌────────────────────┴─── REPLAY (forever, no LLM) ──────┐
   AI agent calls   │                                                        │
   member.savings-  │   step machine → locator ladder → checkpoint           │
   balance(100042)  │        │                                               │
                    │        ├── success + typed outputs                     │
                    │        ├── business outcome (MEMBER_NOT_FOUND)          │
                    │        ├── recovered (dismissed a popup, retried)      │
                    │        ├── blocked (risky action, no approval)         │
                    │        └── escalated → human takes the live session    │
                    └────────────────────────────────────────────────────────┘
```

Plus, because you can't practise on a real bank system, **you build the bank system too** — a deliberately awful fake credit-union console with framesets, nested tables, no test IDs, IDs that regenerate every render, and switchable faults (not found, permission denied, slow load, surprise popup, session timeout, HTTP 500). That's not cheating; the brief explicitly invites *"an intentionally hostile surface."* Building it is what lets you demonstrate every error path on demand.

## 6. What they're grading, in their order

| Weight | Row | Where you win it |
|---|---|---|
| 1 | **System design** | The artifact schema and the replay result contract. Clean boundaries, sensible models, appropriate simplicity. |
| 2 | **Core loop correctness** | The agent really completes a real goal; the artifact really replays and verifies success. |
| 3 | **Robustness & error handling** | The three-way split: business outcome vs. recoverable vs. hard failure. Locator, wait, and checkpoint strategy. |
| 4 | **Human-in-the-loop** | A real lease, real context in the intervention, real resume — "not just a TODO." |
| 5 | **Generalization** | Credible story for desktop/legacy surfaces and for 100s of tenants sharing one vendor product. |
| 6 | **Safety** | Allowlist, risky-action gating, redaction. |
| 7 | **Code quality** | Readable, typed where it counts, easy to run. |
| 8 | **Communication** | REPORT.md makes the reasoning and the cut lines clear. |

They say explicitly: **breadth is not rewarded.** A thin-but-real version of *every* requirement beats a polished version of three. And "say what you cut and why" is a scored instruction, not a courtesy — cutting deliberately and documenting it reads as judgment.

## 7. The four sentences to have ready

If you can say these cold and defend each one, you're in good shape.

1. **"I don't record selectors, I record identity."** Role, accessible name, and the data context the control sits in — then I re-derive a locator at replay through a ranked ladder that requires a unique match. That's why the artifact survives IDs that regenerate every render, and why the same design would work on a desktop app.

2. **"Business outcomes are declared in the schema, not caught as exceptions."** 'No such member' is a typed result the calling agent can read in the capability's contract before it ever invokes it. Conflating that with a crash is the mistake the brief warns about, and I solved it at the schema layer.

3. **"The artifact is compiled from what actually worked, not from the model's transcript."** The recorder logs executed actions with verified postconditions; the compiler prunes anything that didn't change state. That decoupling is why replay doesn't inherit the model's mistakes.

4. **"Handing control back is a re-orientation problem, not a resume-from-a-line-number problem."** The human may have done more, less, or something different than I asked. So I re-observe and let the assertions tell me where I actually am — and if none of them hold, I raise a second intervention rather than guess.
